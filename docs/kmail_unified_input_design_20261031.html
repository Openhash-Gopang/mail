K-Mail 통합 입력창 설계안

mail.hondi.net/desktop.html · 작성일 2026-10-31 · 나만의 AI 비서(pro core) + 문서 작성 SP + 메일 SP(편지 작성·캠페인)를 입력창 하나로 통합

1. 확정된 결정 사항

항목결정
기본 모드입력창 기본값은 나만의 AI 비서(pro core SP)를 호출한다.
서류 모드서류 드롭다운에서 카테고리를 선택하면 해당 카테고리의 문서 작성 SP를 호출하고 서류 작성 화면을 펼친다.
메일 모드입력창 왼쪽 메일 아이콘 하나에 팝오버를 붙이고, 팝오버 항목은 편지 작성(AI), 캠페인 2개로 한다.
빠른 발송AI SP를 호출하지 않는 폼 화면이므로 왼쪽 메뉴에 유지한다.
SP 구조화면은 통합, SP는 분리 유지. 모드 전환 시 SP를 교체(스왑)하며 한꺼번에 합쳐 보내지 않는다.
모드 표시입력창 안에 칩으로 현재 모드를 표시하고 × 로 해제한다. 하위 모드까지 표시한다(예: "메일 · 캠페인").
자동 라우팅기본 모드에서 서류·메일 의도가 감지되면 전환을 제안하고, 사용자가 승인해야 전환한다.

5. SP 호출 흐름

  1. 페이지 로드 시 mode = "default", 활성 SP는 pro core로 설정한다.
  2. 서류 드롭다운 선택 또는 메일 팝오버 선택 시 mode와 submode를 갱신하고, 활성 SP를 해당 SP 하나로 교체한다.
  3. 사용자 입력은 항상 "현재 활성 SP 1개 + 대화 내역"만 모델에 전달한다. 다른 모드의 SP는 요청에 포함하지 않는다.
  4. 모드 해제(×) 시 활성 SP를 pro core로 되돌리고, 진행 중이던 작업 상태는 임시보관함에 저장한다.
SP를 하나로 합치지 않는 이유: 토큰 낭비와 지시 충돌을 막고, 편지(산출물 1통)와 캠페인(수신자 목록·일정·성과 추적)처럼 산출물이 다른 작업을 각자의 SP에서 독립적으로 개선할 수 있기 때문이다.

자동 라우팅 제안 (기본 모드 한정)

pro core SP에 한 줄 규칙을 추가한다: "사용자 요청이 서류 작성 또는 메일 발송 의도로 판단되면 직접 처리하지 말고, 해당 모드 전환을 제안하는 응답(전환 대상 모드 포함)을 반환한다."

  • 제안은 응답 안의 버튼 형태(예: [서류 작성 모드로 전환])로 표시하고, 클릭 시에만 SP를 교체한다.
  • 사용자가 제안을 무시하면 기본 모드에서 계속 대화한다.
  • 전환 시 원래 입력 문장을 새 모드의 첫 입력으로 이어 넘긴다.

6. 왼쪽 메뉴 변경

제거 (입력창으로 이동)

  • 문서 작성 (서류 드롭다운으로 이동)
  • 메일 > 편지 작성(AI)
  • 메일 > 새 캠페인

유지

  • 빠른 발송 (폼 화면, SP 미호출)
  • 내 캠페인, 주소록
  • 편지쓰기, 임시보관함, 보낸메일함, 받은메일함, 태그별 보관함
  • 소개 페이지, 모바일 화면, 사용법
  • 행정 업무 > 정보 공개 청구
"문서 작성" 메뉴 항목을 제거하면 기본 화면 자체가 통합 입력창이 된다. 사이드바 최상단의 활성 항목을 무엇으로 둘지(예: "홈" 또는 "AI 비서")는 구현 전에 결정이 필요하다.

7. 모바일 대응

  • 입력창이 좁아 클립·메일·서류 드롭다운을 모두 노출할 수 없으므로 "+" 버튼 하나에 첨부 / 서류 / 메일(편지 작성·캠페인)을 모은다.
  • 모드 칩은 입력창 위쪽 별도 줄에 표시한다.
  • 기존 "모바일 화면" 메뉴 항목과의 관계(별도 페이지 유지 여부)는 구현 시 확인한다.

8. 위험 요소와 대응

위험대응
사용자가 현재 모드를 인지하지 못함칩 + 아이콘 강조 + 모드별 인사말·플레이스홀더로 3중 표시
SP 지시 충돌·토큰 증가요청마다 활성 SP 1개만 전달(스왑 구조)
모드 전환 중 작업 손실전환 전 임시보관함 자동 저장
자동 라우팅 오작동제안만 하고 승인 시에만 전환
3개 화면 통합에 따른 회귀기존 문서 작성·편지 작성·캠페인 화면의 동작을 모드별 체크리스트로 검증 후 배포

9. 구현 전 확정이 필요한 남은 항목

  1. 메일 · 편지 작성 / 메일 · 캠페인 모드의 인사말·플레이스홀더 문구
  2. 사이드바 최상단 활성 항목의 이름(문서 작성 제거 후)
  3. 서류 모드에서 입력창을 하단으로 내릴지, 현재 위치를 유지할지
  4. 기존 desktop.html·모바일 페이지·SP 파일의 실제 구조 확인 (구현 착수 시 현재 저장소 상태 기준으로 진행)
