K-Mail은 사용자가 자연어로 요청하는 메일 발송·주소록 관리·인바운드 필터 규칙을, 대화를 통해 정확한 구조화 데이터로 확정한 뒤 실제로 실행하는 혼디넷의 메일 비서입니다.

탄생 의도는 여기서 한 걸음 더 나갑니다 — 상대방도 K-Mail을 쓴다면, 사람과 사람이 며칠씩 메일을 주고받던 조율을 K-Mail과 K-Mail이 직접 여러 차례 주고받는 방식으로 바꿔, 의사결정의 속도·정확성·합리성을 끌어올리는 것이 목표입니다. 이 자율성의 범위는 K-Plan(기획)이 정하고, 범위 밖은 반드시 사람에게 옵니다 — 아래 K-Plan과의 관계 참고.

관리자 전용 공문 시스템(gov-mail, hondi.org)과는 완전히 무관합니다 — 여기서 다루는 건 혼디 사용자 개인의 메일(<guid>@hondi.kr)입니다.

할 수 있는 일

기본 3가지 — 발송, 주소록, 자동삭제 규칙

평소엔 자연어로 대화하고, 실행이 필요한 순간에만 K-Mail이 내부적으로 구조화된 액션을 냅니다. 사용자는 이 내부 형식을 몰라도 됩니다.

1
메일 발송(즉시 또는 예약)
한 명 또는 여러 명에게 보낼 수 있고, 회신을 특정 시각까지 모아 다이제스트로 정리해줄 수도 있습니다. 발송 대상은 그 자리에서 자동으로 주소록에도 등록됩니다. 캠페인에는 이름(title)을 붙여 나중에 다시 찾을 수 있고, 수신자마다 다른 본문(맞춤 초안)을 보낼 수도 있습니다.
2
주소록 등록·검색·관리
이름·이메일·직업·소속기관·전공·나와의 관계·그룹(태그)으로 저장·검색합니다. 그룹 부여/해제, 중복 연락처 병합도 대화로 처리합니다.
3
규칙 등록 — 자동삭제 또는 위임 처리
"불필요한 메일은 도착 즉시 삭제해" 같은 자동삭제 규칙뿐 아니라, "이런 요청이면 확인 안 받고 알아서 답장해" 같은 위임 처리 규칙도 자연어 그대로 등록합니다. 실제 판정은 이 문장을 다른 AI가 그대로 읽고 수행합니다. 자세한 내용은 위임과 에스컬레이션 참고.
4
캠페인 조회·보고서
"저번에 서울대 교수들한테 보낸 캠페인 명단이랑 내용 보여줘" 같은 질문에 실제 수신자 명단·본문으로 답합니다. "기관별 응답률 정리해줘"라고 하면 기관·카테고리별 발송·회신·응답률을 집계한 보고서를 만들고, "종료해줘"라고 하면 그 자리에서 캠페인을 종료 처리합니다.
캠페인 생애주기

업무용 메일은 이 7단계로 진행합니다

K-Mail은 업무용 메일이므로, "누구한테 뭘 보낼까요"부터 시작하지 않습니다. 사용자가 여러 단계를 한 번에 말해주면 해당 단계는 확인만 하고 건너뜁니다 — 순서를 기계적으로 다시 밟지 않습니다.

1목적 파악 — 무엇을 위한 메일인지 먼저 확인
2대상 검색·특정 — 모호하면 실제 웹 검색을 거쳐 후보 확정
3주소록 반영 — 발송 확정 시 신규 수신자 자동 등록
4발송 — 캠페인 이름(title)·수신자별 맞춤 본문(선택) 확인 후 확정
5회신 취합 — 마감 시각까지 자동으로 회신을 모아 다이제스트 생성
6보고 — 다이제스트 자동 전달, 요청 시 기관별 응답률 보고서
7종료·기록 — 명시적 요청 시 종료 처리, 언제든 다시 검색·인출 가능 SP v1.7~v1.8 신설
모든 캠페인은 발송 확정 즉시 영구 기록됩니다 — 나중에 "저번에 보낸 캠페인 뭐였지" 같은 질문에 이름·수신자 명단·본문까지 그대로 찾아 보여줄 수 있습니다.
정직한 한계 — 반드시 지키는 원칙

이메일 주소를 스스로 지어내지 않습니다

K-Mail은 이메일 주소를 스스로 알고 있지 않습니다. 수신자를 확보하는 방법은 사용자가 직접 알려주거나, 모호한 서술("서울대 컴퓨터 관련 학과 교수들")에 대해 실제 웹 검색을 거쳐 스니펫에서 실제로 확인되는 정보만 후보로 제시하는 것, 이 둘뿐입니다. 검색 결과에 이메일이 안 보이면 지어내지 않고 "못 찾았다"고 솔직히 말합니다.

⚠
이메일 주소 추측·확정 금지 — 검색으로도 확인되지 않는 이메일은 후보에 넣지 않고, 사용자에게 직접 물어봅니다.
⚠
발송 전 명시적 확인 필수(위임 범위 밖 발송) — 위임 규칙 범위 안이 아닌 이상, 수신자 명단·제목·본문·발송 시각을 한 번에 정리해 보여주고 "이대로 보낼까요?" 확인을 받은 뒤에만 실제 발송을 확정합니다.
⚠
GDC 초과 과금 누적액 미집계 — 발송 현황 조회에서 아직 잡히지 않습니다. 물어보면 "그 항목은 아직 집계가 안 됩니다"라고 솔직히 답합니다.
⚠
실사용자 대화 경로의 K-Plan 연동 — 부분 검증 — 관리자 시딩 경로로 다이제스트→K-Recompose 파이프라인은 end-to-end 검증됐지만, 실사용자가 채팅 중 직접 플랜을 언급하는 경로와 신설된 사전 질의(K-Plan에 실시간으로 판단을 구하는 경로)는 아직 실사용자 트래픽으로 검증되지 않았습니다.
⚠
위임 규칙 자동 승격은 사후 검토 없음 — K-Plan이 반복 가능한 패턴이라고 스스로 판단하면 위임 규칙을 즉시 만듭니다. 과하게 일반화됐는지 검증하는 절차는 아직 없어, 오판이 그대로 규칙화될 수 있습니다 — 사람이 주기적으로 위임 규칙 목록을 확인하는 걸 권장합니다.
⚠
실시간 상태(재고·영업시간 등)는 사람이 직접 입력 — K-JIT 같은 실시간 연동은 아직 없어, K-Plan의 판단은 사람이 입력해둔 값이나 계획서의 정적 맥락에 근거합니다.
K-Plan과의 관계

K-Plan은 기획팀, K-Mail은 그 지시를 실행하는 front line

K-Mail은 무엇을, 왜, 누구에게 보낼지 스스로 기획하지 않습니다 — 그건 K-Plan의 역할입니다. K-Mail은 K-Plan의 계획을 실제 사람(또는 상대측 K-Mail)과의 메일 왕복으로 구현하는 실무 담당입니다.

사람K-Plan (기획팀)K-Mail (front line)
결정하는 것새 정책, 큰 그림 승인왜/누구에게/몇 단계로, 체크포인트마다 뭘 확인할지지금 이 사람에게 뭐라 쓸지, 이 회신이 스팸인지 진짜 문의인지
시간 축필요할 때만 개입여러 주에 걸친 계획 전체지금 이 순간의 대화 하나하나
실패 시방향 재승인계획 재수립(K-Recompose)스레드를 어떻게 이어갈지 재시도·에스컬레이션

3단계 처리 원칙

메일 한 통이 왔을 때 어느 등급으로 처리할지는 [메일의 성격 × 지금의 실제 상태]로 정해집니다 — 메일 종류만으로는 정해지지 않습니다. 예: "짜장면 2그릇 주문"은 재고·시간 여유가 있으면 2단계(즉시 처리), 없으면 3단계(사람 승인 필요)가 됩니다.

1
즉결
되돌릴 필요조차 없는 일. 예: 스팸 삭제. 보고 없이 로그만 남습니다.
2
위임 범위 내 실행
K-Plan이 미리 정해둔 조건 안. K-Mail이 사람 확인 없이 직접 실행하고 K-Plan에만 보고합니다.
3
신규 판단 필요
전례 없음·위임 범위 밖. K-Plan과 사람 모두에게 올라갑니다. 예: 시청 위생 점검 통보.

함수 수준 API — 실시간으로 묻고 즉답받습니다

K-Plan과 K-Mail은 같은 서버 안에 있어 실제 HTTP 왕복 없이 함수 호출로 연결됩니다. K-Mail이 판단이 안 서는 인바운드를 만나면, K-Plan에게 그 자리에서 물어보고 즉답을 받습니다 — "K-Plan이 답을 안 준다"는 상황 자체가 없습니다(매번 동기 LLM 호출 1회로 즉답).

_kplanDecideForKMail({ planId, subject, bodyText, threadHistoryText }) → { decision: 'approve' | 'escalate', replyGuidance?, urgent?, holdMessage?, suggestedRuleText?, delegationPromoted? }

K-Plan은 플랜의 목표·계획서, 실시간 상태(재고·영업시간 등, 사람이나 향후 K-JIT 연동이 채워넣는 값), 이 상대와의 과거 대화 이력까지 근거로 판단합니다. 승인이면서 반복 가능한 패턴이라고 스스로 판단하면, 그 자리에서 위임 규칙으로 자동 승격해 다음부터는 안 물어봐도 되게 만듭니다. 에스컬레이션이면서 급한 사안이면, 사람 확인 전 "확인 후 회신드리겠습니다" 같은 대기 응답까지 K-Plan이 직접 문구를 정해 K-Mail에게 시킵니다.

기존 상향 보고 — K-Recompose

캠페인이 여러 트랙으로 나뉘어 몇 주에 걸쳐 순차 발송될 때, 사용자가 "이 캠페인은 K-Plan 플랜의 일부"라고 명시적으로 알려주면 회신 다이제스트가 K-Plan의 중간 재평가(K-Recompose)를 자동으로 트리거합니다.

1사용자가 "이 캠페인은 K-Plan 플랜 X의 체크포인트야"라고 알림
2KMAIL_SEND_CAMPAIGN에 kplan_plan_id 포함(명시했을 때만 — 추측 금지)
3회신 마감 시각 도달, 다이제스트 생성
4K-Plan의 K-Recompose 자동 트리거, plan 레코드에 실제로 저장 2026-09-04 수정
5조정 결과가 사용자 메시지함에 노출, plan.hondi.net에서도 대화 이력으로 확인 가능
검증 상태 — 관리자 시딩 → 스윕 → K-Recompose → 결과 조회까지 end-to-end 성공(2026-09-02, 라이브 스모크테스트). 2026-09-04에 재평가 결과가 사용자 메시지함에만 쓰이고 plan 레코드 자체(대화 이력·체크포인트 카운트)는 갱신 안 되던 공백을 수정했습니다. 실사용자 채팅 경로와 신설 사전 질의 API는 아직 라이브 검증 전입니다.
위임과 에스컬레이션

상대방도 K-Mail을 쓴다면 — K-Mail과 K-Mail이 직접 대화합니다

기존 이메일은 사람이 사람에게 쓰고 AI가 대신 써주는 틀입니다. K-Mail은 이걸 한 단계 더 밀어붙입니다 — 위임 범위 안의 요청이면 사람 확인 없이 K-Mail이 직접 회신까지 보냅니다. 두 조직의 조율이 "사람이 메일 확인 → 며칠 뒤 답장"이 아니라 양쪽 K-Mail이 그 자리에서 여러 차례 주고받는 방식이 되면, 의사결정 속도·정확성·합리성이 크게 올라간다는 것이 이 설계의 목적입니다.

A
위임 규칙 등록
"짜장면·짬뽕류 주문이고 재고·시간 여유 있으면 바로 수락해" 같은 자연어 규칙을 등록합니다. 특정 K-Plan 캠페인/체크포인트로 범위를 좁힐 수도, 전역으로 둘 수도 있습니다.
B
자동 승인·회신
인바운드가 위임 범위 안으로 판정되면, K-Mail이 사람 확인 없이 즉시 회신을 작성해 발송합니다. 처리 결과는 항상 기록되어 나중에 확인할 수 있습니다.
C
에스컬레이션
범위 밖이거나 애매하면 사람에게 올립니다. 급한 사안이면 K-Plan이 대기 응답 문구까지 정해줘서, 사람 확인 전에 "확인 후 회신드리겠습니다"를 먼저 보낼 수 있습니다.
스레드 단위로 추적됩니다 — 같은 상대와의 대화는 open(진행 중) / pending_kplan(K-Plan 응답 대기) / pending_human(사람 확인 대기) / resolved(처리 완료) 4단계로 관리되고, 판단할 때마다 그 상대와의 과거 왕복 이력(최근 8건)을 함께 참고합니다 — 이번 메일 한 통만 보고 판단하지 않습니다.
사람과의 관계

자율성이 늘어난 만큼, 최종 승인 경계는 더 명확합니다

위임·에스컬레이션 체계가 생겼다고 K-Mail이 사람 없이 무엇이든 결정하는 건 아닙니다 — 오히려 "어디까지는 사람 없이 가고, 어디부터는 반드시 사람을 거치는지"가 이전보다 훨씬 명시적으로 나뉘었습니다.

●
위임 범위는 사람(또는 K-Plan)이 정합니다 — K-Mail이 스스로 "이 정도는 물어보지 않아도 되겠다"고 위임 범위를 넓히지 않습니다. 범위를 정하는 건 위임 규칙을 등록하는 사람, 또는 그 규칙을 승격시키는 K-Plan입니다.
●
범위 밖은 예외 없이 사람에게 옵니다 — 애매하면 항상 안전한 쪽(에스컬레이션)으로 판정합니다. 금액·계약·확정적 약속이 걸리거나 전례 없는 사안은 자동 처리 대상이 아닙니다.
●
대기 응답과 최종 답변은 다릅니다 — 급한 사안에 "확인 후 회신드리겠습니다"를 먼저 보내는 것은 판단을 대신하는 게 아니라 시간을 버는 것뿐입니다. 실제 결정은 사람의 확인을 거친 뒤에만 나갑니다.
●
위임 규칙은 언제든 사람이 고치거나 지울 수 있습니다 — K-Plan이 자동으로 승격한 규칙도 예외가 아닙니다. 과하게 일반화됐다고 판단되면 그 규칙을 좁히거나 삭제하는 것으로 즉시 되돌릴 수 있습니다.
●
발송 대상·본문은 항상 확인 대상입니다(위임 범위 밖) — 수신자 명단·제목·본문·발송 시각을 한 번에 정리해 보여주고 확인을 받은 뒤에만 실제 발송을 확정합니다.
