나비웹 서버리스 메일 아키텍처 설계

v0.1 설계안 · 2026-11-13 · 대상: naviweb.kr 메일(ceo@naviweb.kr 포함) · 근거: Openhash-Gopang/hondi, Openhash-Gopang/mail 저장소 코드·문서 읽기(운영 서버·Cloudflare 설정은 직접 확인하지 못한 부분을 §12에 적음)
한 줄 요약 — 메일을 "서버에 쌓인 편지"가 아니라 나비 채팅과 같은 봉투(서명·해시체인·수신확인)에 담은 AI 간 메시지로 보고, 저장은 사용자별 사서함(Durable Object)과 암호화된 객체 저장소(R2)가 맡고, L1~L5 원장에는 해시만 앵커링한다.
  • 서버 없음: 메일 경로에 상시 서버가 없다. Cloudflare 수신 → 워커 → 사서함 DO → R2. L1 PocketBase는 메일 저장소가 아니라 원장 노드로만 남는다(내려가도 메일은 흐른다).
  • 두 통로: 나비웹 ↔ 나비웹은 SMTP 없이 채팅과 같은 전달 계층으로 직통(네이티브 레인), 외부 인터넷 메일과는 브리지 레인으로만 연결한다.
  • OpenHash 연동: 사서함마다 해시체인 h_i = SHA-256(h_{i-1} ‖ data_i ‖ height_i), 메일 중요도에 따라 PLSM이 앵커링 계층(L1~L5)을 고른다. 보냄·도착·읽음이 원장 항목이 된다.
  • 솔직한 한계: 외부에서 SMTP로 들어오는 메일은 워커에 도착하는 순간 평문이다. 즉시 봉인(암호화)하고 평문은 보관하지 않지만, "수신 순간까지 E2E"는 불가능하다(§6).
  • 다음 한 걸음(§11 Phase 0): naviweb.kr에 Email Routing catch-all을 켜 기존 워커(naviweb.kr 수신 코드는 이미 있음)에 연결. 설계 확정과 무관하게 바로 할 수 있다.

4. 두 개의 통로

4.1 네이티브 레인 — 나비웹 ↔ 나비웹 (SMTP 없음)

  1. A의 개인 AI가 메시지 봉투를 만든다(§5). 수신자 bob@naviweb.kr는 등록부 DO에서 B의 guid로 해석.
  2. A의 지갑 키로 서명 → 게이트웨이 워커가 서명 검증(채팅 /signal/*와 같은 방식, 쿠키 또는 auth/issue 토큰).
  3. B의 사서함 DO가 순서를 매겨 봉인된 본문을 R2에 두고, 해시체인 머리를 갱신. A의 보낸 사서함에도 같은 해시로 기록.
  4. B가 접속 중이면 실시간 연결로, 아니면 Web Push로 알림(채팅과 동일 계층). B가 열면 delivered → acknowledged 영수가 A의 사서함에 쌓인다.
  5. 외부 인터넷을 전혀 거치지 않으므로 스푸핑·평문 노출 구간이 없다. 본문은 A 기기에서 B의 공개키로 봉인된 채 B 기기에서 열린다(진짜 E2E).

4.2 브리지 레인 — 외부 메일

수신: 외부 → Email Routing → 게이트웨이 워커 → (SPF/DKIM/DMARC 결과·차단 목록·속도 제한 확인) → 즉시 사용자 공개키로 봉인하고 평문은 버린다 → 사서함 DO. 수신자 AI가 의도(intent)를 추출해야 하는 경우만 §8의 위임 복호화를 쓴다.

발신: 사용자 서명 확인 → 게이트웨이가 send_email로 발송(주소 <아이디>@naviweb.kr, DKIM 서명) → 보낸 사서함에 해시 기록. 외부 수신 서버가 읽는 순간부터는 나비웹의 통제 밖이다.

브리지는 신뢰 경계다 — 같은 도메인 naviweb.kr이라도 "서명된 네이티브 메시지"와 "외부에서 온 메일"을 UI에서 구분해 표시한다(스푸핑 방지). 네이티브 메시지는 지갑 서명 검증을 통과한 것만 그렇게 보인다.

5. 메시지 봉투 — 채팅과 메일은 같은 봉투의 두 가지 배달 방식

채팅과 메일을 별개 시스템으로 두지 않는다. 지금 ai_messages가 이미 session_id, sender_guid, receiver_guid, content_type으로 둘 다 담는다. 이를 서명된 봉투로 승격한다.

envelope = {
  v: 1,
  id:        "<UUIDv7>",                 // 시간순 정렬 가능
  thread:    "<session_id>",             // 채팅·메일 공용 스레드
  from:      "<guid>",   to: ["<guid>" | "ext:<이메일>"],
  kind:      "mail" | "chat" | "call" | "receipt" | "digest",
  intent:    { type, params, deadline? },  // 개인 AI가 읽는 구조화 부분(선택)
  body_ct:   "<봉인된 본문 → R2 참조>",   // 사람이 읽는 부분(암호문)
  atts:      [{ r2, ct_hash, size }],
  prev:      "<보낸 사람 체인 직전 해시>",
  importance: 0..100,                      // §7 PLSM 입력
  ts, sig:   Ed25519(sender, hash(envelope without sig))
}

배달수신자 온라인 → 실시간수신자 오프라인 → 사서함에 보관 후 푸시

스레드가 같으므로 사용자는 한 대화 안에서 채팅과 메일을 이어 본다(kmail:<campaignId> 같은 기존 세션 규칙 유지). 외부 수신자(ext:)에게는 평문 MIME으로 변환해 브리지로 나간다.

6. 암호화와 키

구간방식서버가 평문을 보는가
네이티브 ↔ 네이티브보낸 기기가 수신자 공개키(X25519)로 봉인(sealed box). 서명은 Ed25519아니오
외부 → 나비웹 (수신)워커가 도착 즉시 수신자 공개키로 봉인, 평문 폐기수신 순간 메모리에서만(보관 안 함)
나비웹 → 외부 (발신)사용자 서명 후 워커가 MIME 변환·발송발송 순간 메모리에서만
보관(R2·DO)암호문과 해시, 최소 메타(수신자 guid, 시각, 크기, 상태)아니오

키 구조

  • 지갑 Ed25519(서명)와 별도의 X25519 암호화 공개키를 사서함 DO에 등록한다(서명키를 재사용하지 않는다). 개인키는 기기 IDV 볼트.
  • PDV 백업 방식 C와 동일: 복구 문구로 열리는 DEK에서 HKDF로 메일 키를 유도 → 폰을 잃어도 복구 가능, 복구 문구를 잃으면 복구 불가(PDV 조사서의 미결정 항목과 같은 정책 결정 필요).
  • PC는 영구 키를 갖지 않고, 폰 승인 후 세션 동안만 복호화(PC 로그인 ≠ PDV 접근 원칙과 일치).
한계 (숨기지 않는다) ① 외부 SMTP 메일은 도착 순간 워커에서 평문이며, 이는 어떤 메일 서비스도 같다. ② 메타데이터(누가·언제·크기)는 라우팅에 필요해 서버가 안다. ③ 봉인된 메일은 서버 쪽 검색·AI 요약이 불가능하다 → 검색 색인은 기기에서 만들어 암호화 백업하거나 위임 복호화(§8)를 쓴다.

7. OpenHash 연동 — 해시체인, 계층 앵커링, 수신확인

메일용 중요도 점수 (제안)

OpenHash 원안은 score = w1·금액 + w2·유형 + w3·계약이다. 메일은 금액이 없으므로 다음으로 대체하되 값은 사용자 선택이 아니라 서버가 정한 규칙이다(tiers.js·plsm.js는 그대로 두고 입력만 바꾼다).

요소예가중(제안)
발신 신분기관 인증 발신(official_access_cert 계열) / 개인 / 미확인 외부0.4
문서 유형공문·통지·계약 / 일반 서신 / 자동 알림0.4
회신·기한 요구기한 있는 요청, 다단계 합의0.2

LCAT(발신자와 수신자의 최하위 공통 계층)은 두 사람의 L1 노드 소속으로 계산한다. 같은 읍면동이면 L1~L2에서 끝나고, 타 지역·외국이면 상위 계층에 앵커링된다. 표 값(%)은 openhash_integrated_v1.md §3.1의 표1을 그대로 쓴다.

8. 개인 AI의 자율 처리와 동의

K-Plan↔K-Mail 설계(KPLAN_KMAIL_AGENT_TO_AGENT_ARCHITECTURE)의 3단계 처리를 그대로 쓴다. 메일 한 통이 오면 메일의 성격 × 지금 상태로 등급이 정해진다.

단계정의보고복호화
1 즉결스팸 삭제 등 되돌릴 필요 없는 일로그만필요 없음(발신 신뢰도·헤더만 사용)
2 위임 범위 내 실행사전 위임 조건 안AI 비서(K-Plan)위임 복호화
3 신규 판단전례·위임 밖AI 비서 + 사람사용자 기기에서만
위임 복호화(선택 기능) — 사용자가 "자동 응답·분류를 서버 쪽 AI가 해 달라"고 명시적으로 켠 경우에만, 사용자가 서명한 범위·기간이 있는 위임 토큰으로 게이트웨이 워커가 해당 메일을 메모리에서만 복호화해 의도를 추출한다. 위임·사용은 모두 원장에 해시로 남고(DELEGATED_READ), 언제든 철회할 수 있다. 끄면 E2E가 유지되고 자율 처리는 기기가 켜져 있을 때만 동작한다. 기본값은 꺼짐이다.

응답이 없거나 사람 개입이 필요하면 양쪽 AI가 각자 사람에게 고지한다(P3). 고지는 기존 _sendPushToGuid를 쓰고 request_id를 태그에 싣는다.

9. 신뢰성·남용 방어·운영

문제대응
L1 서버 중단메일 경로는 L1을 쓰지 않는다. 앵커링은 사서함 DO의 대기열에 쌓았다가 복구 후 일괄 전송(수신 시 "L1 조회 실패 → 반송" 경로 제거)
사서함 쓰기 경합DO가 같은 guid 요청을 자동 직렬화 → seq·prev_hash 충돌 없음
없는 주소등록부 DO 조회 후 SMTP 단계에서 즉시 거부(현재 _kmailRejectUnknownRecipient 동작과 동일). 바운스 폭탄(backscatter) 방지
스팸·폭주발신자·IP 속도 제한, 기존 kmail_blocklist 규칙을 사서함 DO 설정으로 이관, SPF/DKIM/DMARC 결과를 점수화
스푸핑네이티브는 서명 검증, 외부는 "외부" 배지. 같은 naviweb.kr 주소를 사칭한 외부 메일은 DKIM·서명 불일치로 격하
메일 아이디 변경옛 아이디 예약 기간 정책 필요(현재 코드 주석에도 "상용 개시 전에 다시 정할 것"으로 남아 있음)
보존·삭제보존 기간 지나면 R2 객체와 DO 색인 삭제, 해시와 영수는 원장에 남는다(내용은 복원 불가, 존재 증거만 유지)
비용DO·R2는 사용량 과금. 저장 과금은 기존 storage_next_billing_at·GDC 과금 체계와 연결

10. 사서함 데이터 모델 (DO 내부 SQLite, 제안)

messages(
  seq INTEGER PRIMARY KEY,          -- 사서함 안 순번 (직렬화됨)
  id TEXT UNIQUE, thread TEXT,
  dir TEXT,                         -- in | out
  lane TEXT,                        -- native | bridge
  peer TEXT,                        -- guid 또는 ext:이메일 해시(원문 주소는 봉인 영역)
  kind TEXT, importance INTEGER,
  state TEXT,                       -- sent | delivered | acknowledged | expired | blocked
  body_ref TEXT, size INTEGER,      -- R2 키 / 암호문 크기
  env_hash TEXT, h_prev TEXT, h_self TEXT, height INTEGER,
  ts INTEGER
)
anchors(batch_id, from_seq, to_seq, merkle_root, tier, status)   -- 앵커 대기열·결과
receipts(env_hash, kind, sig, ts)                                -- 영수 해시
prefs(delegation, auto_reply, blocklist, retention_days, ...)     -- 현재 kmail_user_settings 이관
keys(enc_pub_x25519, node_sig_key_id)                              -- 공개키만

11. 이행 단계

"기존 사용자는 새로 시작"이 확정돼 있으므로 옛 메일 이관은 필요 없다. 단계마다 되돌릴 수 있게 둔다.

단계내용검증위험
0naviweb.kr Email Routing 활성화, catch-all → 기존 워커. 코드 변경 없이 외부 메일 수신 시작(저장은 지금의 L1 PocketBase). ceo@는 K-Mail 아이디로 소유자가 다시 가입해 받는다테스트 메일 도착 확인낮음
1사서함 DO + 메일 아이디 등록부 DO 도입, write-through(DO와 PocketBase 양쪽에 기록). 읽기는 DO 우선두 저장소 불일치 점검중간
2X25519 키 등록·봉인(R2 암호문). 수신 즉시 봉인. 기기 복호화. 복구 문구 연계기기별 열람, 복구 시험높음(키 분실=영구 소실 정책 결정 필요)
3네이티브 레인(SMTP 없는 직통) + 영수 + 푸시두 계정 왕복, 오프라인 수신낮음
4사서함 해시체인, 중요도·PLSM 앵커링, 영수 원장 항목체인 검증기(브라우저·서버 공용)중간
5PocketBase 메일 테이블 읽기 전용화 → 폐기. L1은 앵커 전용메일 경로에서 L1 호출 0건낮음

ceo@naviweb.kr의 위치

L1 서버에서 확인한 결과, 메일 아이디 ceo는 kmail_user_settings에 소유자 guid와 함께 있고(서명 "도 영민(주피터)") 외부 메일함 주소는 없다. 소유자의 profiles 레코드는 현재 조회되지 않는다. guid가 전화번호에서 결정적으로 계산된다는 문서(GDUDA_P2P_Design_v2.md) 기준이 지금도 맞다면, 같은 전화번호로 다시 가입하면 같은 guid가 되어 ceo 아이디를 이어받을 가능성이 높다(코드로 재확인 필요). 단계 0만으로 ceo@naviweb.kr는 이 K-Mail 사서함으로 들어온다. 외부 Gmail로 전달은 하지 않는다(선택 2번).

12. 결정이 필요한 것과 확인하지 못한 것

결정 1 — E2E와 AI 자율의 우선순위: 기본은 E2E(위임 복호화 꺼짐)로 두는 안을 제안한다. 켜면 K-Mail이 기기 밖에서도 자동 응답하지만 서버가 그 순간 평문을 본다.
결정 2 — 키 복구 정책: 복구 문구를 잃으면 메일은 영구 소실. PDV 백업과 같은 정책으로 갈지, 별도 위탁 복구(예: 신뢰하는 두 사람의 분산 보관)를 둘지.
결정 3 — 기관 메일의 앵커링 계층: 공문 등 고중요도 메일을 L4(국가 기관)까지 올릴지는 L4 노드 운영 주체와의 약정에 달려 있다. 현재는 L1~L3까지만 실사용 가능한지 확인이 필요하다.
결정 4 — 외부 발신 한도·과금: 무료 가입 보너스 안에서 외부 발송 몇 통까지 허용할지(스팸 오용 방지, 도메인 평판 보호).

이 설계에서 직접 확인하지 못한 것

  • naviweb.kr의 Cloudflare Email Routing 현재 상태(수신 규칙·MX). 이전 세션에서 발송용 바운스 MX가 있음은 보았으나 수신 규칙은 확인하지 않았다.
  • send_email 바인딩의 외부 수신자 발송 허용 범위와 Cloudflare 수신 메일 크기·속도 한도(공식 문서로 재확인 필요).
  • Durable Object 저장 한도·비용 단가, 사서함 수가 수만 이상일 때의 운영 비용(추정하지 않았다).
  • L1~L5 실제 노드의 이중 서명·앵커링 경로가 메일 규모를 받을 수 있는지(OpenHash 문서는 실험 수치만 있다).
  • X25519 암호화 키를 지갑 키에서 유도할지 별도 생성할지(지갑 코드 gopang-wallet.js 점검 필요).
