1역할과 모드

태블릿의 주된 용도는 스마트폰 화면의 확대다. naviweb.kr은 PC에서 접속하면 desktop.html, 폰에서 접속하면 webapp.html을 연다. 이동 중에도 폰으로 desktop.html을 쓰기 위한 방법이 태블릿이다. 인증과 통신은 스마트폰이 맡고, 화면과 입력(키보드, 트랙패드, 마우스, 펜)은 태블릿이 맡는다.

이 페이지의 하드웨어와 OS 설명은 나비웹 전용 모드를 기준으로 한다.

2구성: 세 개의 물리적 축

나비웹은 태블릿, 스마트폰, 클라우드 세 축으로 이루어진다. 지금은 스마트폰 하나가 이 가운데 폰과 태블릿의 역할을 겸한다. XO+ 단말은 폰이 하던 일에서 화면과 입력을 분리한 것이다.

태블릿스마트폰클라우드
역할화면, 입력, 승인, 서명인증, 메신저와 통신, PDV 저장, 촬영·문서 인식, 서명LLM 추론

연결블루투스(제어·알림), Wi-Fi Direct 또는 폰 핫스팟(대용량)이동통신, Wi-Fi인터넷

스마트폰만으로도 같은 소프트웨어가 동작한다. 태블릿을 더하면 화면과 보안이 올라가는 추가 구성이다. 폰과 태블릿은 각자 서명 키를 가지며 키를 복사하지 않는다.

화면은 태블릿이 직접 그린다

전용 모드의 태블릿은 desktop.html을 직접 실행해 화면을 그린다. 폰 화면을 영상으로 받아 보여 주는 방식(화면 미러링)은 쓰지 않는다. 지연이 없고, 폰이 곁에 없어도 문서 편집과 PDV 열람이 계속되며, 배터리와 전송량 부담이 작기 때문이다.

폰과 태블릿의 통신

용도수단
페어링, 근접 확인, 깨우기, 서명 요청 알림블루투스(BT)
대용량 데이터(PDV 동기화, 문서)Wi‑Fi Direct 또는 폰 핫스팟
서버와의 통신폰이 중계하거나 태블릿이 직접 연결한다. 중계 프로토콜은 WebRTC 기반으로 시작해 블루투스와 Wi‑Fi Direct로 바꿀 수 있게 만든다.

지금의 기기 연동(QR 90초 세션, X25519 + AES‑GCM 봉투)은 폰의 개인 키를 PC로 복사하는 구조다. 태블릿은 키를 따로 가지므로 이 방식을 그대로 쓰지 않는다. 태블릿이 만든 공개 키만 등록하는 절차를 둔다.

폰이 없거나 망이 끊겨도 서명, PDV 열람, 문서 편집은 계속한다. 연결이 돌아오면 폰이 한꺼번에 전달한다.

사진 첨부: 두 기기가 하나의 단말처럼

태블릿의 서류 작성 화면에서 [폰으로 촬영]을 누르면 폰의 나비 카메라가 열린다. 폰이 윤곽 인식, 기울기 보정, 문자 인식을 처리해 결과를 태블릿의 첨부란으로 보낸다. 원본은 PDV에 저장되고, 첨부했다는 사실은 서명으로 OpenHash에 남는다.

3사용 형태

같은 소프트웨어와 같은 서명 구조를 두 가지 형태의 기기에서 쓴다.

그림은 개념을 나타내는 그림이며 실제 제품의 모양이 아니다.

① 폰 + 태블릿 결합② 폴드형 폰(둘을 합친 한 기기)
구성스마트폰과 태블릿이 따로 있다. 폰은 주머니에 두고, 태블릿에 키보드와 트랙패드(마우스, 펜)를 붙여 쓴다.접으면 폰, 펼치면 태블릿이 되는 한 기기. 펼친 화면에 키보드와 트랙패드를 연결해 쓴다.
화면태블릿이 desktop.html을 직접 실행한다.펼치면 desktop.html, 접으면 폰 화면(webapp.html)이다.
서명 키폰과 태블릿이 각자 키를 가진다(키 2개).한 기기에 키 하나. 접어도 펼쳐도 같은 키다.
폰 ↔ 태블릿 연결블루투스와 Wi‑Fi Direct로 연결한다.필요 없다. 한 기기 안에서 처리한다.
장점화면·입력과 보안이 분리된다. 하나를 잃어도 남은 기기로 복구한다. 태블릿은 저가형으로 만들 수 있다.하나만 들고 다닌다. 연결 과정과 두 번째 기기 비용이 없다. 이동 중에도 큰 화면을 쓴다.
유의점두 기기를 함께 챙겨야 하고, 연결이 끊기면 폰의 중계를 쓰지 못한다.기기를 잃으면 키와 PDV가 함께 사라진다. 두 번째 기기가 없으므로 복구용 백업 키와 암호화 백업이 반드시 필요하다.

폴드형 폰의 조건

  • 접이식 화면을 가진 한 기기가 폰의 역할(인증, 통신, PDV)과 태블릿의 역할(화면, 입력, 승인)을 함께 맡는다.
  • 기기 등급은 폰과 같은 기준으로 판정한다. 하드웨어 보안 영역의 키를 서버가 증명으로 검증하고, 최신 OS와 최근 보안 패치를 쓰면 A 등급이다.
  • 서명 확인은 서명 전용 버튼이나 지문 같은 하드웨어 경로로 한다. 승인 화면은 펼친 화면이 서명 대상 원문으로 직접 그린다.
  • PDV는 암호화해 클라우드나 사용자가 지정한 곳에 백업한다. 폰과 태블릿 두 곳에 백업하는 구조는 쓸 수 없으므로, 두 번째 기기가 없는 형태에서는 이 백업이 유일한 복원 경로다.
  • 두 번째 기기(폰이나 태블릿)를 더하면 ①의 구조로 올라가, 한쪽을 잃었을 때 남은 기기로 복구한다.

②는 구상 단계의 사용 형태이며, 나비웹 전용 모드를 폴드형 기기에서 실행하는 방식은 시제품에서 검증한다.

4하드웨어

핵심은 연산 성능이 아니라 하드웨어 서명과 선명한 화면이다. 영화나 게임을 위한 기기가 아니다.

화면: 화질이 최우선

  • 10~11인치급 고해상도 화면. 글자의 선명도가 우선이다.
  • 밝기와 색 재현을 확보하고, 눈부심 방지 표면과 깜박임 없는 밝기 조절을 갖춘다. 주변 밝기에 따라 밝기와 색온도를 자동으로 맞춘다.
  • 한글 글꼴과 글자 렌더링 품질을 처음부터 설계에 포함한다.

입력

하드웨어 키보드, 트랙패드, 한글 입력기를 갖춘다. 마우스와 펜도 쓸 수 있다. 검토 중 수정과 AI 비서 지시를 편하게 하기 위해서다.

보안과 부품

부품내용
보안 칩외부 보안 칩에 서명 키를 보관한다. 키는 기기 밖으로 나가지 않는다.
사용자 확인서명 전용 버튼이나 지문 같은 하드웨어 경로. 일반 키보드를 거치는 PIN 입력은 신뢰하지 않는다.
연결블루투스와 Wi‑Fi(Direct 포함). 이동통신 모뎀은 두지 않는다.
시계와 난수배터리 백업 시계(서명 시각의 신뢰), 하드웨어 난수 발생기

사양 방침

  • 고성능 그래픽 칩은 필요 없다. 화면 합성과 스크롤이 부드러운 수준이면 된다.
  • 연산 성능과 메모리는 낮추고, 연산은 스마트폰과 클라우드가 맡는다. 필요한 메모리는 실제 브라우저로 측정해 정한다.
  • 저장 용량은 작게 잡는다. 원본은 스마트폰과 클라우드에 있다.
  • 카메라, GPS, NFC, 이동통신 모뎀은 최소화하거나 제외한다. 이 기능은 스마트폰이 맡는다.
  • 제품 단계에서는 셸, 디버깅 포트, 개발자 모드를 제거한다.
  • 제조 과정에서 제조사가 키를 보지 못하게 하고, 공장에서는 정품 증명만 넣는다.

5OS와 브라우저

XO+ OS는 윈도우나 리눅스 같은 거대한 OS가 아니다. 최소한의 리눅스 위에서 나비웹 전용 브라우저 하나가 전체 화면으로 실행되는 구조이며, 브라우저에 필요한 OS 기능만 더한다. 앱 실행기와 앱 스토어는 두지 않는다.

기능내용
부팅과 변조 방지서명된 부트로더와 커널만 실행한다. 시스템 영역은 읽기 전용이다.
서명 모듈보안 칩의 키로 서명한다. 패스키(FIDO2/WebAuthn) 표준과 호환된다.
모드 분리일반 모드로 바꾸면 전용 영역(키, PDV)은 분리되어, 일반 모드의 앱이 읽을 수 없다.
입력·화면한글 입력기, 글꼴, 자동 밝기·색온도 조절
업데이트서명된 이미지로만 원격 업데이트. 이전 버전으로 복구할 수 있다. 보안 패치 시점은 서버가 기기 등급을 판정할 때 쓴다.

콘텐츠와 껍데기를 나눈다

  • 콘텐츠(나비웹 사이트와 문서)는 스크립트 없는 정적 HTML5로 그린다. 콘텐츠 영역에서는 JavaScript를 끌 수 있어 공격 면이 크게 줄어든다.
  • 껍데기(승인 화면과 기기 화면)는 서명된 로컬 코드만 실행한다. 외부 콘텐츠는 여기에 접근할 수 없다.

문서는 HTML5 하나

  • PDF 뷰어, 오피스, 한글 뷰어가 필요 없으므로 코드와 메모리, 공격 면이 함께 줄어든다.
  • 외부에서 받은 docx, pdf, hwp는 스마트폰, 클라우드, 또는 PC의 나비웹 도우미에서 HTML5로 변환해 단말로 보낸다. 기관이 PDF나 한글 파일을 요구할 때의 반대 방향 변환도 같다.
  • 원본은 PDV에 그대로 보관하고 해시를 남긴다. 법적 증빙은 원본을 기준으로 한다.
  • 문서용 HTML5 프로필(허용 요소, 스크립트 금지, 정규화된 직렬화)을 정의해, 같은 문서는 항상 같은 해시가 되게 한다.

기존 웹은 부가 기능, 엔진

  • 기존 웹을 방문하더라도 별도 프로필의 격리 모드로 열고, 서명 기능에는 접근하지 못하게 한다.
  • 엔진은 상위 프로젝트의 보안 패치를 계속 받는 것(Chromium 계열, 임베디드용 WebKit 등) 가운데, 쓰는 기능만 남기는 방향으로 시제품에서 비교해 정한다.

6서명과 신뢰

승인 흐름: 화면에 보이는 것 = 서명되는 것

  1. 나의 AI 비서가 작업 안건을 만든다. 예: 서류 제출, 계약 승인.
  2. 안건이 스마트폰을 거쳐 태블릿으로 전달된다.
  3. 태블릿이 서명될 내용 그대로를 화면에 보여 준다. 위험도가 높은 안건은 구분해 표시한다.
  4. 사용자가 검토한 뒤 서명 전용 버튼 같은 하드웨어 확인 동작으로 승인한다.
  5. 보안 칩이 내용의 해시에 서명하고, 그 결과가 OpenHash에 기록된다.

승인 화면은 폰이 보낸 이미지가 아니라 태블릿이 서명 대상 원문으로 직접 그린다. 폰만 쓸 때도 폰이 같은 방식으로 서명한다. AI 비서의 작업 지침은 서명된 데이터로 관리하고, 하드웨어가 서명을 확인한 갱신만 받아들인다. 클라우드는 응답에 어떤 버전의 지침으로 수행했는지 해시를 붙여 기기가 검증한다.

서명 주체와 기기 등급

폰과 태블릿 둘 다 서명한다. 폰의 보안 수준은 이미 상당하므로 폰 단독 서명도 허용하되, 아이폰 수준의 보안을 요구한다. 기종 목록이 아니라 기기가 증명하는 보안 수준으로 등급을 정한다. 새 기종이 나와도 목록을 관리할 필요가 없고, 보안 패치가 끊긴 기기는 자동으로 내려간다.

등급조건
A최신 갤럭시·아이폰 수준하드웨어 보안 영역(Secure Enclave, StrongBox)의 키를 서버가 증명으로 검증했고, 최신 OS와 최근 보안 패치를 쓴다. XO+ 태블릿도 여기에 든다. 기준은 2026년 11월의 최신 기종 수준이다.
B그 외증명이 안 되거나, 보안 영역이 약하거나, 패치가 오래된 기기.
거부등록 불가루팅·부트로더 해제 기기.

패치가 끊기면 A에서 B로 자동으로 내리고 사용자에게 알린다. 등급은 서명할 때마다 서버가 증명 결과로 다시 확인하며, 기기가 스스로 알리는 등급은 믿지 않는다.

한도 수치는 예시이며 운영하면서 조정한다. 결제 밖의 작업은 사용자가 하려는 일의 중요도에 따라 하위·구형 기종의 범위를 제한한다.

서류 중요도

처음에는 제출처로 나눈다. 학교 제출 서류나 민원 신청서처럼 취소·정정이 쉬운 서류는 B 등급도 낼 수 있다. 법원이나 등기소처럼 되돌리기 어려운 곳, 계약 체결, 재산권 변동은 A 등급 기기로 승인해야 한다. 이후 서류 종류별로 세분화한다.

구현 원칙

  • 일·월 누적 한도는 서버가 집계하고 강제한다. 기기 안에서만 확인하면 우회된다.
  • B 등급 폰이라도 A 등급 기기(태블릿)가 함께 서명하면 A 한도를 쓰는 안을 선택지로 둔다.
  • OpenHash에는 해시만 남기고, AI 비서의 지시문은 서명해 해시를 남긴다.
  • 접속 대상은 나비웹 출처와 폰 연결로 제한한다.
  • 보안 부팅, 읽기 전용 시스템, 서명된 업데이트를 갖추고, 브라우저 보안 패치를 몇 주 안에 배포하는 체계를 둔다.
  • 대량 배포 전에 독립된 보안 감사와 침투 테스트를 받는다. 안전은 크기가 아니라 설계가 만든다.

7분실과 복구

폰과 태블릿은 각자 키를 가진다(복사하지 않는다). PDV는 암호화해 두 기기 모두에 백업한다. 둘 중 하나를 잃어도 남은 기기로 복구한다.

단계처리
1. 정지남은 기기에서 분실 기기의 키를 즉시 정지한다. 정지는 기다리지 않고 할 수 있다.
2. 폐기분실 기기의 공개 키를 등록에서 지우고 OpenHash에 기록한다.
3. 새 기기 등록새 기기가 새 키를 만들고, 남은 A 등급 기기가 승인한다. 탈취에 대비해 알림 뒤 대기 시간을 둔다.
4. PDV 복원남은 기기의 백업으로 새 기기의 PDV를 되살린다.
  • 남은 기기가 B 등급 폰이면 기기 등록·폐기·복구를 직접 할 수 없으므로, 오프라인으로 보관하는 복구용 백업 키로 처리한다.
  • 두 기기를 한꺼번에 잃으면 복구용 백업 키와 본인 확인 절차로만 복구한다.
  • 폰만 분실해도 PDV는 암호화되어 있어 읽을 수 없다.
  • 폴드형 폰 하나만 쓰는 경우에는 남은 기기가 없으므로, 복구용 백업 키와 암호화 백업으로만 복구한다.

8출시 계획

  • 2026년 말 · 시험: 일부 태블릿 브랜드 제품을 대상으로 XO+ 운영체제(OS)를 시험하고 있다.
  • 2027년 · 출시 목표: 100달러 가격이 목표다. OLPC가 내건 ‘100달러 노트북’과 같은 가격대다. 키패드·마우스·트랙패드를 포함하며, 단말 가격과 실제 원가의 차이는 나비웹 플랜으로 충당하는 구상이다.
  • 특화: 나비웹과 ‘나만의 AI 비서, 나비’에 특화한 기기다. 나비웹 사용자 1천만 명 모집을 상정해 보급 계획을 작성하고 있다.

개발 순서

단계내용상태
1. 서명 흐름기기 등록과 승인 안건 서명 흐름을 스마트폰과 PC 브라우저에서 먼저 검증한다.예정
2. 중계 프로토콜서명·암호화한 안건을 폰이 저장했다가 전달한다. 전송은 WebRTC로 시작해 블루투스와 Wi‑Fi Direct로 바꿀 수 있게 만든다.예정
3. 지침 관리서명된 AI 비서 지침의 버전 관리, 클라우드 응답의 지침 해시 검증예정
4. 정식 앱구글 승인 후 안드로이드 정식 앱. 블루투스 상시 중계에 필요하다.예정
5. 시제품시판 개발 보드에서 경량 OS, 브라우저 엔진, 한글 입력, 글꼴, 메모리를 검증한다.예정
6. 하드웨어보안 칩, 화면, 키보드 사양을 확정하고 제조 파트너를 선정한다.예정

제조 파트너는 아직 정하지 않았다. 부품 변경 금지, 메모리 가격 변동 조항, 키 주입 금지, 설계 소유권을 계약 조건으로 요구할 계획이다.

9정해야 할 것

  • 미결A 등급이 인정하는 보안 패치 기간
  • 미결기기 등록·폐기 때 알림 뒤 대기 시간의 길이
  • 미결복구용 백업 키의 보관 방식
  • 미결폴드형 폰에서 나비웹 전용 모드를 실행하는 방식(접힘·펼침 전환, 키보드 연결)
  • 미결브라우저 엔진 선택과 실제 메모리 하한 측정
  • 미결사용자 확인 방식(서명 전용 버튼, 지문)
  • 미결iOS 스마트폰 지원 범위(PWA의 제약이 큼)
  • 미결공공 도입에 필요한 암호 모듈 검증 요건 확인
